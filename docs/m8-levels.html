三条路（handoff ③.2 列的）

(a) 给 frame 加回 ctx

frame?: (node: N, ctx: FrameContext) => NodeFrame
type FrameContext = { nodes: Readonly<Record<AnyNodeId, AnyNode>> }

// parametric-node-renderer.tsx
const nodes = useScene((s) => s.nodes)              // ← 代价在这一行
const frame = def?.frame?.(effective, { nodes }) ?? IDENTITY_FRAME

代价，按份量排：

  1. 每一个节点的渲染器都要订阅整张 nodes 表。 现在是 useScene((s) => s.nodes[nodeId])（node-renderer.tsx:17）—— 改一堵墙只有那堵墙重渲染。改成整表订阅之后， 任何一次场景改动都会让 N 个 ParametricNodeRenderer 重渲染， 而 useNodeEvents 每次返回新的处理器对象 （use-node-events.ts:32-52）⟹ R3F 每次都要重新挂 handler。
    不是每帧——拖拽走 live overrides，根本不碰 store（use-live-overrides.ts）。 是每次提交 / 新建 / 删除。100 堵墙的场景里落一堵墙 = 100 次重渲染。 这不是 M4 「只移动鼠标时一次不重算」那条目标本身，但方向是反的。
  2. 逃生口存在，但走进逃生口之后 (a) 就变成 (e)。 要让「只有需要的 kind 才订阅整表」，只能按标志分成两个渲染器组件 （hooks 不能条件调用）。那个形状就是下面的 (e)，只是绕了一圈。
  3. 它把「位姿可以依赖别人」变成所有 kind 的通用能力，而这个能力现在只有一个用户。 D10 的 rule of three 说的正是这件事：第三个用户出现时才抽。 现在抽，签名是对着一个用例猜的。

(a) 有一个容易被低估的优点：四个已有实现一行都不用改。 TS 的结构类型允许「少参数的函数」满足「多参数的类型」， frame: wallTransform 继续编译。 这让 (a) 看起来比实际便宜——真正的代价在渲染器那一侧，不在实现那一侧。

(b) 走 def.system，每帧命令式写 obj.position.y

对照仓库的做法。packages/viewer/src/systems/level/level-system.tsx，77 行，我读过全文。

代价，四条：

  1. 给节点定位从此有两条路。 D19 选真父子的第一条理由是「I1 的强制方式：交给场景图，不可能算错」。 第二条路一开，「一个节点坐在哪」的答案从「读 def.frame」变成 「读 def.frame，除非有个 system 每帧改写它」。 本项目已经有 8 个「写出来像对的、verify 全绿、功能静默死掉」的 bug， 全部长在「靠自觉记住一条规则」上。
  2. 动画是买一送一的，但 M8 不需要动画。 ROADMAP 的 M8 只要「当前层实心、下层灰显、上层隐藏」——那是可见性，不是位置。 对照仓库需要 lerp，是因为它有 exploded 模式（每层 ordinal × 5）和层重排； 两样都不在 M8 范围内。为一个不做的功能付一条并行路径。
  3. 照抄会黑屏，而且 verify 全绿

    对照仓库写的是 useFrame(cb, 5)——priority 非 0， 注释说「lower priority so it runs after transforms from other systems have settled」。

    实测 @react-three/fiber 9.7.0（项目 node_modules 里那一份）： subscribe(ref, priority, store) 在 priority > 0 时执行 internal.priority = internal.priority + 1 （dist/events-b1bdeb1a.cjs.dev.js:1146，注释原文 "it takes rendering into its own hands … we switch off automatic rendering"）， 而渲染那一行是 if (!state.internal.priority && state.gl.render) state.gl.render(...) （同文件 :16196）。 任何一个 priority > 0 的 useFrame 都会整个关掉自动渲染。 对照仓库有自己的渲染循环，我们没有。抄过来 = 一片黑。

  4. 帧序耦合。OpeingGhost 在 useFrame 里读 host.localToWorld(...)（opening-tool.tsx:148）。 层的 Y 由另一个 useFrame 写，两个都在 priority 0 ⟹ 顺序 = 挂载顺序。 幽灵可能晚一帧。声明式没有这个问题：React 提交时位置就已经是对的。

(c) 把算好的 elevation 塞进 computeLevelData

这条路不是贵，是走不通。三个理由，逐条对着代码：

  1. computeLevelData 的结果只喂给 def.geometry （geometry-system.tsx:66-72），渲染器读不到； 而位姿是渲染器写的（parametric-node-renderer.tsx:33-34）。
  2. 它只在该 kind 有脏节点时才算（geometry-system.tsx:28-39）。 层的 Y 必须永远是对的，包括没有人变脏的那一帧。
  3. 顺序反了：层的位姿要在几何之前确定，而 computeLevelData 在几何管线里面。

要让 (c) 成立，必须把它搬出 GeometrySystem、搬到渲染器能读到的地方—— 搬完之后它就是 (a)。

(c) 里唯一该留下的东西是记忆化： getLevelElevations 用 WeakMap 以 nodes 记录本身为键 （对照仓库 storey.ts:59-66）。 我们的 useScene 每次改动也是整体替换 nodes （use-scene.ts:65 / 88 / 109 三处都是 { ...s.nodes }），同一个技巧直接可用。 它和选哪条路无关，(a)(b)(e) 都要它。

§02机制说明

十一件事 · A–K

A · 三个容器 core

Site → Building → Level，三个都是 BaseNode 的直接扩展。 比对照仓库瘦得多——它的 SiteNode 有 polygon + terrain， BuildingNode 有 position + rotation， LevelNode 的 children 收窄到 25 种 id 联合。 我们三样都不要：BaseNode.children 是 string[]，够用； polygon/terrain 在 D2 的排除清单里；position/rotation 见 J。

Level 的三个字段，一个一个都有讲究：

字段类型含义为什么这么写
levelz.number().default(0) 序数，不是标高 规格书 Gotchas 第一条：ordinals are semantic。 < 0 是地下室，=== 0 是首层。不许重新编号
baseElevationz.number().default(0) 附加偏移，累加 它抬高本层，并且连带抬高同一栋楼里所有更高的层。见 B
heightz.number().positive().optional() 层高（floor-to-floor） 绝对不许写 .default()。见 D

B · 层的世界 Y 是算出来的 core

算法 12 行，照抄对照仓库 storey.ts:87-98：

按 ordinal 升序排序
cumulative = 0                      // 每栋楼各一个
for 每一层:
    baseY      = cumulative + level.baseElevation
    cumulative = baseY + level.height
两个反直觉的结论，各配一条测试钉死

① baseElevation 是累加的。 它进了 baseY，而 baseY 又喂给 cumulative。 给一层 +0.3，二层的 baseY 是 2.8，不是 2.5。 规格书原文也这么写。没有测试钉住的话，将来一定有人把它「修」成非累加。

② 有地下室时，首层不在 y=0。 栈是从最低序数开始从 0 往上堆的。加一个 level: -1 的地下室（层高 2.5）之后： 地下室 baseY = 0，首层 baseY = 2.5。 这不是 bug，是算法的定义——把首层拉回 0 的正确做法是给地下室 baseElevation = -2.5（因为它累加，首层跟着回到 0）。 这正是 baseElevation 存在的理由。

记忆化：WeakMap 以 nodes 记录本身为键 （对照仓库 storey.ts:59-66，注释说的是 WallCutout 每帧每墙问一次、 一帧重建过 1000+ 次同样的 Map）。 成立的前提是 useScene 每次改动整体替换 nodes—— use-scene.ts:65 / 88 / 109 三处都是 { ...s.nodes }。 把这个前提写进注释：将来谁把 store 改成原地 mutate，这个 memo 会静默返回旧值。

C · 容器怎么渲染出来 viewer

前置 A 第 1 条：现在的 NodeRenderer 会让容器连同整棵子树消失。

// node-renderer.tsx:20-30 —— 现在
const def = nodeRegistry.get(node.type)
if (!def) return null
if (def.renderer) { ... }
if (def.geometry) return <ParametricNodeRenderer node={node} />
return null                          // ← 容器掉进这里，整棵子树没了，不报错

改法是把兜底从 null 换成通用渲染器：没有 geometry 的节点在 GeometrySystem 里本来就走 clearDirty + continue （geometry-system.tsx:49-52），不会有副作用。 通用渲染器已经会做容器需要的全部三件事：注册进 sceneRegistry、 应用 frame、递归渲染 children（parametric-node-renderer.tsx:39-41，M7 铺的）。

容器必须退出选中订阅 —— 不是「反正射线打不到它」

直觉是：容器没有 mesh，射线打不到，所以 level:click 不会发。错的。

实测 @react-three/fiber 9.7.0 （dist/events-b1bdeb1a.cjs.dev.js:668-678）：每一个命中都会沿 object.parent 一路向上， 把每一个带 handler 的祖先都推进 intersections。 点一堵墙，level:click 一样会发，而 SelectionManager 按 nodeRegistry.entries() 订阅了每一个 kind （selection-manager.tsx:21-23）。

现在能不出事，只是因为 onNodeClick 里那句 e.stopPropagation() 恰好跑在前面（同文件 :806：if (localState.stopped === true) break）—— 一个靠执行顺序成立的巧合，正是 D15 说的「依赖注册顺序的代码不可调试」。 而且它只在选中启用时成立：isSelectionEnabled() 为 false 时那句 stopPropagation 根本不执行。

对照仓库把这件事写在 packages/nodes/src/level/definition.ts 的 capabilities 注释里，原话： "Level is a container — selection happens via the sidebar tree and the floating level switcher, never via 3D click. Declaring selectable here would make getSelectableKinds() add the kind to SelectionManager's subscription list, and the event would fire on every wall/slab/ceiling click that bubbled to the level group — selecting the level instead of the actual node hit." 所以 NodeDefinition 加一个 selectable?: boolean（默认 true）， 容器写 false，两处消费：SelectionManager 的订阅列表， 和通用渲染器要不要展开 {...events}。

D · plane-bound 的判据是「字段在不在」 core

wall.height含义改层高时
不在plane-bound——顶跟随层平面跟着变
在explicit——半墙、女儿墙纹丝不动

规格书为这件事写了两条 schema 规则，两条都要照抄：

  1. 意义承载字段不许有 Zod default。 level.height / wall.height / ceiling.height 都是 .optional() 且没有 .default()——absence is data。 我们的 wall.height 和 ceiling.height 已经是对的 （wall.ts:15、ceiling.ts:14），新加的 level.height 别写错。 写了 .default(2.5)，addNode 里的 AnyNode.parse 会把 2.5 物化进节点（use-scene.ts:57），「缺席即数据」当场失效，而 verify 全绿。
  2. store 必须删掉显式 undefined 的 key。 updateNode(id, { height: undefined }) 要移除这个 key， 不是存一个值为 undefined 的 key。见 §04 批 C。

这就是 ROADMAP 说的「M1 那个『不给 default』的决定在这里付息」—— 而且付的是正的息，见 K。

解析器只有两行，但它是整个 M8 的判据： resolveWallTop(wall, storeyHeight) = wall.height ?? storeyHeight。 对照仓库的版本多一个 electedBase 参数（systems/wall/wall-top.ts:26-34）， 那是支撑选举，我们不做。

别写成 wall.height ?? DEFAULT_LEVEL_HEIGHT

那样编译过、测试过（如果测试也传 2.5 的话）、画面看着正常， 但「改层高该层墙跟着变」这条验收永远不会通过—— 而它看起来只是一个 fallback 常量的选择。 本项目第 2 个「类型系统看不见」的 bug（M2 常量选错）就是这个形状。

E · 层内相对标高 —— 一次还掉 M6 的两条债 core viewer

M7 的 def.frame + 真父子已经保证：层的 group 一动，它的孩子全跟着动。 所以「层内相对标高」不需要任何复合代码，只需要把三个数的基准从世界改成层内：

东西M7（世界）M8（层内）还掉哪条债
墙[0, height][0, resolveWallTop(wall, 层高)]M1「墙高无楼层概念」
楼板[0.05 - t, 0.05][-t, 0]M6「墙陷进楼板 5 cm」
天花[2.5, 2.5 + t]（常量）[层高 - margin, …]M6「天花不吸附层顶」
原方案行不通，改成 Z —— 工作约定第 6 条

对照仓库怎么让墙站在楼板上的：支撑选举。 墙的底标高 = 它脚下那块楼板的 elevation（默认 0.05）， 所以墙站在楼板上、墙身高度是 2.45（resolveWallEffectiveHeight = top - electedBase）。 那需要 computeWallSlabSupport：覆盖判定（边界包含的带状重叠， 因为自动楼板的多边形来自墙中心线，墙正好落在多边形边上）+ 多块楼板取最高 + supportSlabId 持久化。整个不在 M8 范围内。

M8 改成：层内 0 就是行走面。 DEFAULT_SLAB_ELEVATION 从 0.05 改成 0， 楼板占 [-thickness, 0]（它本来就是向下长的，slab/geometry.ts:20-21）， 墙底 0，两者严丝合缝。

代价，两条，都进 §06： ① 和对照仓库差 5 cm 的约定，M9 做存档格式时要知道这件事； ② 抬高的露台 / 下沉的客厅做不了——那需要选举。

⚠ 注意 slab.elevation 有 .default(0.05) 并且会被物化进节点 （前置 A 第 8 条）。所以改默认值只影响新建的楼板； 同一次运行里已经建出来的老楼板还带着 0.05。 没有持久化 ⟹ 刷新即清空 ⟹ 语料是空的，但 如果你在同一次运行里对比新旧楼板，会看到 5 cm 的错位，那不是 bug。

F · siblings 的语义修正 viewer

GeometrySystem 现在按 kind 分组算 computeLevelData （geometry-system.tsx:25-39、:60-64）。 多楼层一来这是个真 bug：calculateLevelMiters 收到全场景的墙， 一层和二层在同一个 XZ 交点上的两堵墙会互相斜接。

改成按 (kind, parentId) 分组。这不是优化，是修 bug—— 而且名字对上了：对照仓库里 level 就是楼层， calculateLevelMiters 本来就是「一层楼的墙」。 M5 把它做成了 per-kind，M8 把语义还回去。

副作用（好的那种）：siblings 从此对所有 kind 都表示「同一个宿主下的同类」。 M11 楼梯在楼板上挖洞时要的正是这个粒度。

G · 「当前层」与四个工具 app

handoff ③.5 说的「M8 的第一个真问题」。它会同时碰四个工具，外加两处不那么明显的地方：

  1. parentId：三个工具的 addNode 各加一个字段 （门窗不改，它的宿主是墙）。
  2. 射线平面：eventToGround(e, el, camera) → eventToGround(e, el, camera, baseY)。 planeY 形参早就在（前置 A 第 11 条），一直用的默认 0。
  3. 预览 / 幽灵的 Y：三个预览都挂在 Canvas 根下、画在世界 PREVIEW_Y = 0.01（前置 A 第 4 条）。
  4. 吸附与联动：documentWalls() → levelWalls(levelId) （前置 A 第 5 条）。

第 2 条有个陷阱：在 plan 视图里看不出差别。 顶视正交相机的射线是垂直的，XZ 与平面高度无关—— 所以改对了和没改一样，只有 3D 透视下才露馅。 不要因为「看着没变」就以为这一条没生效或者不需要。

第 3 条建议做成一个组件（比如 <LevelFrame>），把三个预览包起来， 而不是每个工具自己加 baseY——M12 加新工具时会第四次撞到这件事。 对照仓库的同名东西叫 LevelOffsetGroup，注释原话： "the ghost renders at world ground on upper floors while the cursor raycast rides the floor plane — they drift apart."

「当前层」自己要能自愈： resolveCurrentLevelId(preferred, nodes)——preferred 还在就用它， 不在就取 ordinal 最小的层，一个层都没有就 null。 撤销撤过了建层那一步时，这条救命（虽然 §04 批 H 会让那一步根本不进历史）。

H · 楼层显示是 app 层的可见性，不是位置 app

ROADMAP：「当前层实心、下层灰显、上层隐藏」。 三件事全是 presentation，全是命令式，而且全在 app 层—— 因为「当前层是哪一层」是编辑体验，D4 不许 viewer 知道 （viewer 现在连 selectId 都是当 prop 收的，viewer.tsx:19）。

📌 sceneRegistry.byType 终于有了第一个读者。 这条债从 M1 记到现在（「有写入无读者」，scene-registry.ts:7,21）， M7 明确说过不会还，M8 还。 对照仓库的第一个读者也正是它的 LevelSystem（level-system.tsx:29）。

两个必须知道的实现约束：

  1. 灰显必须每帧重写，不能只在切换时写一次。 GeometrySystem 在节点变脏时会整个换掉子节点、dispose 掉材质 （geometry-system.tsx:74-78、:95-103）—— 你上一帧调过的那个材质已经不存在了。 对照仓库的 applyShadowOnly 注释说的就是这件事： "apply re-runs every frame so meshes rebuilt while hidden get re-hidden."
  2. useFrame(cb)，绝对不要 useFrame(cb, 5)。 理由和实测行号在前置 B 的 (b) 第 3 条——priority > 0 会整个关掉自动渲染， 画面全黑，verify 全绿。这是本 M 最容易「照抄对照仓库」照出来的事故。
    顺序不用担心：GeometrySystem 挂在 <Viewer> 内部、 {children} 之前（viewer.tsx:40 / 42）， 两边 priority 都是 0 ⟹ 订阅顺序 = 挂载顺序 ⟹ 几何先重建、可见性后覆盖。

I · 脏传播：改层高要脏它的孩子 core

updateNode 现在脏化自己 + 父（use-scene.ts:94-97）。 M8 要加上孩子——只加一层，不是整棵子树。 依据是规格书 Gotchas 的原文："A level.height change dirties that level's walls / stairs / ceilings / fences."

不加的话：改层高 → level 自己进脏集 → 它没有 geometry → clearDirty → 墙一堵都不重建。数据对了，画面没变。

⚠ 别顺手改成「整棵子树」：removeNode 已经在走 collectSubtree （use-scene.ts:104），两处语义混在一起会让「拖一堵墙」脏化整层。

J · 不变量：Level 只做 Y 平移 core

这条不变量是本 M 一半改动量的来源，写进注释

Site 和 Building 是单位矩阵，Level 只有 position.y。 推论：世界 XZ ≡ 层内 XZ。

所以所有工具的 XZ 数学——eventToGround 返回的点、snapToGrid、 wallStart/wallEnd、linkedWallOverrides 的量化键、 斜接的交点检测——一行都不用改。 M8 只碰 Y。这就是为什么 §04 只有十个批次而不是三十个。

什么会破坏它：给 BuildingNode 加 position / rotation（对照仓库有， packages/core/src/schema/nodes/building.ts:11-12）。 加了之后当场坏掉的第一个地方是 OpeingGhost 的 host.rotation.y（opening-tool.tsx:149， 那是局部旋转，位置那一行用的却是走完整链的 localToWorld）—— 门的幽灵会以正确的位置、错误的朝向贴在墙上。 所以 M8 主动不加，到 M13 真要摆两栋楼时， 连同 getWorldQuaternion 一起改。已进 §06。

K · 「迁移」这个词在 M8 到底指什么 core

ROADMAP 写的是「迁移：wall.height → level.height （第一次真实 schema 迁移）」。按工作约定第 6 条，这里要显式更正一下措辞：

  • 没有数据可迁。这个项目现在没有任何持久化 （「刷新即丢，无存档」是 STATE.md 里挂在 M9 的债）。语料是空的。
  • 真正发生的是语义迁移：同一个字段 wall.height， 从「墙的高度，缺席时取常量 2.5」变成「墙的显式高度，缺席即 plane-bound」。 这是本 M 的主体，它在代码里，不在迁移函数里。
  • 还是要写一个 migrateToLevels(snapshot) 纯函数，两个真实用途： ① 开机脚手架的兜底路径（把散在根下的节点收进层）； ② M9 的预演——M9 要写「版本号 + 迁移链」，这是链条的第一个节点， 趁现在没有存档格式先把形状定下来。

M1 那个「不给 default」的决定在这里付的是正的息： 老墙的 height 本来就不在节点里——getWallHeight 是 读的时候才 ?? 2.5 的（wall.ts:19）。 所以迁移之后它自动变成 plane-bound，层高 2.5， 画面一模一样，一个字段都不用改写。 如果 M1 当初写了 .default(2.5)，今天场景里每一堵墙都会带着一个 显式 2.5，全部变成「半墙」，改层高一堵都不跟着动—— 而且没有任何办法区分「用户真的设过 2.5」和「default 塞的 2.5」。 这就是规格书那两条 schema 规则的全部理由。

import type { AnyNode, AnyNodeId } from '../schema/types'
import { DEFAULT_LEVEL_HEIGHT, getStoredLevelHeight, type LevelNode } from '../schema/level'
import type { WallNode } from '../schema/wall'

export type LevelElevation = {
  /** 本层地面的世界 Y：同栋楼所有更低层的层高与偏移累加到这一层为止。 */
  baseY: number
  /** 本层的层高（已套用兜底）。 */
  height: number
  buildingId: string | null
  /** 序数，不是名次：可以是负数（地下室），可以不连续。 */
  ordinal: number
}

/**
 * 按 nodes 记录的【身份】做记忆化。
 *
 * ⚠ 这条捷径成立的唯一前提是：useScene 每次改动都【整体替换】nodes
 * （use-scene.ts 的 addNode / updateNode / removeNode 三处都是 { ...s.nodes }）。
 * 命中就意味着场景一个字节都没变过。
 * 谁把 store 改成原地 mutate，这里会【静默】返回旧值 —— 不报错，不变红。
 *
 * WeakMap：场景关掉之后不该被这张表钉住。
 */
const elevationMemo = new WeakMap<object, Map<string, LevelElevation>>()

/**
 * 每栋楼各自从 0 起堆：层按序数升序，每层的 baseElevation 抬高它自己
 * 【以及同栋楼所有更高的层】。解析不到楼栋的层共用一个「遗留栈」。
 *
 * 纯函数，只吃序列化过的 nodes。
 */
export function getLevelElevations(
  nodes: Record<AnyNodeId, AnyNode>,
): Map<string, LevelElevation> {
  const memoized = elevationMemo.get(nodes)
  if (memoized) return memoized

  const buildingIds = new Set<string>()
  const levels: LevelNode[] = []
  for (const node of Object.values(nodes)) {
    if (node.type === 'building') buildingIds.add(node.id)
    else if (node.type === 'level') levels.push(node)
  }

  const entries = levels
    .map((level) => ({
      levelId: level.id as string,
      baseElevation: level.baseElevation,
      height: getStoredLevelHeight(level),
      // 对照仓库这里还有一条兜底：parentId 为空时去 building.children 里反查。
      // 我们的 addNode 强制宿主存在并同时写两侧，没有那种半挂的层，所以不做。
      buildingId: level.parentId !== null && buildingIds.has(level.parentId)
        ? level.parentId
        : null,
      ordinal: level.level,
    }))
    .sort((a, b) => a.ordinal - b.ordinal)

  const elevations = new Map<string, LevelElevation>()
  const cumulativeByBuilding = new Map<string | null, number>()

  for (const entry of entries) {
    const baseY = (cumulativeByBuilding.get(entry.buildingId) ?? 0) + entry.baseElevation
    elevations.set(entry.levelId, {
      baseY,
      height: entry.height,
      buildingId: entry.buildingId,
      ordinal: entry.ordinal,
    })
    cumulativeByBuilding.set(entry.buildingId, baseY + entry.height)
  }

  elevationMemo.set(nodes, elevations)
  return elevations
}

/** 本层地面的世界 Y。层解析不到时按 0 —— 场景根就是世界地面。 */
export function levelBaseY(
  levelId: string | null,
  nodes: Record<AnyNodeId, AnyNode>,
): number {
  if (levelId === null) return 0
  return getLevelElevations(nodes).get(levelId)?.baseY ?? 0
}

  nodes: Record<AnyNodeId, AnyNode>,

  if (levelId === null) return DEFAULT_LEVEL_HEIGHT

 * patch 里显式写成 undefined 的 key 会被【删掉】，不是存一个值为 undefined 的 key。
 *

function mergeNodePatch(prev: AnyNode, patch: Partial<AnyNode>): AnyNode {
    const merged: Record<string, unknown> = { ...prev, ...patch }
    for (const key of Object.keys(patch)) {
        if ((patch as Record<string, unknown>)[key] === undefined) delete merged[key]
    }
    return merged as AnyNode
}

export const CEILING_CLAMP_MARGIN = 0.01

/**
 * 宿主层的层高。宿主不是层、或者根本没有宿主时，退回常量。
 *
 * 参数是 resolve 而不是整张 nodes：几何管线里能拿到的就是
 * GeometryContext.resolve（geometry-system.tsx 注入的），
 * 而 app 那边传 (id) => useScene.getState().nodes[id] 也一样能用。
 *
 * 「没有宿主 ⟹ 2.5」是 M8 的过渡态：批 H 之前，所有墙的 parentId 都还是 null，
 * 所以这条兜底让批 F 对现有场景【完全没有视觉变化】。批 H 之后它只兜真错误。
 */
export function hostStoreyHeight(
  parentId: string | null,
  resolve: (id: AnyNodeId) => AnyNode | undefined,
): number {
  if (parentId === null) return DEFAULT_LEVEL_HEIGHT
  const host = resolve(asNodeId(parentId))
  return host?.type === 'level' ? getStoredLevelHeight(host) : DEFAULT_LEVEL_HEIGHT
}

/**
 * 天花底面的层内标高。判据和墙一样是「key 在不在」：
 *   height 不在 ⟹ 跟着层顶走（层高减一个缝）
 *   height 在   ⟹ 用它自己
 *
 * M8 只做「层高」这一半。对照仓库还会把它压到上层楼板的底面之下
 * （getCeilingClampBound），那一半留到有需要时。
 */
export function resolveCeilingHeight(
  ceiling: Pick<CeilingNode, 'height'>,
  storeyHeight: number,
): number {
  return ceiling.height ?? storeyHeight - CEILING_CLAMP_MARGIN
}

import type { AnyNodeDefinition } from '../../core/registry/node-definition'
import type { AnyNode, AnyNodeId, AnyNodeType } from '../../core/schema/types'

/**
 * 「兄弟」= 同 kind【且】同宿主。
 *
 * 一层楼的墙是兄弟，二层同坐标的墙不是；同一堵墙上的门是兄弟，隔壁墙上的门不是。
 * M5 的 GeometrySystem 只按 kind 分组（全场景的墙都算兄弟），只有一层楼时看不出错；
 * 多楼层之后，一层的墙会和二层同坐标的墙互相斜接。
 *
 * JSON.stringify 而不是拼分隔符：不用去论证「哪个字符不可能出现在 id 里」，
 * 而且 parentId 为 null 和为 '' 天然是两个不同的键。
 */
export function siblingGroupKey(node: Pick<AnyNode, 'type' | 'parentId'>): string {
  return JSON.stringify([node.type, node.parentId])
}

export type SiblingGroups = {
  /** 按 siblingGroupKey 分组的兄弟（已套用 live override）。 */
  siblings: Map<string, AnyNode[]>
  /** 只有声明了 computeLevelData 的 kind 才有这一项。 */
  levelData: Map<string, unknown>
}

/**
 * 为这一帧所有脏节点算好兄弟分组和 levelData，每组只算一次。
 *
 * 从 GeometrySystem 的 useFrame 里抽出来，是因为这一段恰好是最容易「只改一半」的地方：
 * 过滤条件改成按宿主了，缓存的 Map 却还按 kind 当键 —— 那样第二层的墙会
 * 直接复用第一层算好的斜接结果，verify 全绿。留在 useFrame 里就没法测，抽出来就能。
 */
export function computeSiblingGroups(
  dirtyIds: Iterable<AnyNodeId>,
  nodes: Record<AnyNodeId, AnyNode>,
  getDefinition: (kind: AnyNodeType) => AnyNodeDefinition | undefined,
  effective: (node: AnyNode) => AnyNode,
): SiblingGroups {
  const siblings = new Map<string, AnyNode[]>()
  const levelData = new Map<string, unknown>()

  for (const id of dirtyIds) {
    const node = nodes[id]
    if (!node) continue

    const key = siblingGroupKey(node)
    if (siblings.has(key)) continue

    // 按【文档】节点的 parentId 过滤，再套 live override。
    // override 永远改不了 parentId（updateNode 的守卫），所以先后顺序不影响结果，
    // 但先过滤能少 map 一大半。
    const group = Object.values(nodes)
      .filter((n) => n.type === node.type && n.parentId === node.parentId)
      .map(effective)
    siblings.set(key, group)

    const def = getDefinition(node.type)
    if (def?.computeLevelData) levelData.set(key, def.computeLevelData(group))
  }

  return { siblings, levelData }
}

getDefinition 和 effective 作为参数传进来，而不是在函数里直接 import nodeRegistry / getEffectiveNode： 这样测试可以传一个只认墙的桩定义、传恒等函数，不用把整个注册表和 three 拖进测试。 代价是 GeometrySystem 里调用时多写两个参数。

import type { LevelNode } from '../../../core/schema/level'
import { asNodeId, type AnyNode, type AnyNodeId } from '../../../core/schema/types'

// 纯函数：只吃 nodes，不碰任何 store。「当前层」的状态住在 useEditor，
// 怎么从它解析出一个【一定存在】的层，住在这里。

const levelsOf = (nodes: Record<AnyNodeId, AnyNode>): LevelNode[] =>
  Object.values(nodes).filter((n): n is LevelNode => n.type === 'level')

/**
 * 「当前层」的自愈解析。
 *
 *   preferred 还是一个层 → 用它（快路径，O(1)，指针每次移动都会走到这里）
 *   否则                 → 序数 0 的层（规格书：level === 0 是首层）
 *   没有 0               → 序数最小的层
 *   一个层都没有         → null
 *
 * 为什么要自愈而不是信任 useEditor 里存的那个 id：撤销、删除、M9 的导入
 * 都能让它指向一个已经不存在的节点。这里兜住，工具就不用每个都判一遍。
 */
export function resolveCurrentLevelId(
  preferred: AnyNodeId | null,
  nodes: Record<AnyNodeId, AnyNode>,
): AnyNodeId | null {
  if (preferred !== null && nodes[preferred]?.type === 'level') return preferred

  const levels = levelsOf(nodes)
  if (levels.length === 0) return null

  // 同序数时按 id 排，保证结果确定 —— 否则 Object.values 的顺序决定了你落在哪栋楼
  levels.sort((a, b) => a.level - b.level || (a.id < b.id ? -1 : a.id > b.id ? 1 : 0))
  const ground = levels.find((l) => l.level === 0)
  return asNodeId((ground ?? levels[0]!).id)
}

 * 同一栋楼里，往上（+1）或往下（-1）紧挨着的那一层。到头了返回 null。
 * 按序数排序而不是按 level ± 1 查找：序数可以不连续（删过层、插过层）。
 */

  currentId: AnyNodeId | null,
  nodes: Record<AnyNodeId, AnyNode>,
  direction: 1 | -1,
): AnyNodeId | null {
  if (currentId === null) return null
  const current = nodes[currentId]
  if (current?.type !== 'level') return null

  const stack = levelsOf(nodes)
    .filter((l) => l.parentId === current.parentId)
    .sort((a, b) => a.level - b.level)

  const index = stack.findIndex((l) => l.id === current.id)
  const next = stack[index + direction]
  return next ? asNodeId(next.id) : null
}

/** 在某栋楼（或没有楼栋的遗留栈）顶上再加一层时，它该用的序数。 */
export function nextLevelOrdinal(
  parentId: string | null,
  nodes: Record<AnyNodeId, AnyNode>,
): number {
  const ordinals = levelsOf(nodes)
    .filter((l) => l.parentId === parentId)
    .map((l) => l.level)
  return ordinals.length === 0 ? 0 : Math.max(...ordinals) + 1
}

    if (existing !== null) {

        return existing

    } finally {
        release()
    }

    useEditor.getState().setCurrentLevel(levelId)
    return levelId
}

/**
 * 在「当前层所在的那栋楼」顶上加一层，并切过去。
 * 这是用户操作，【要】进历史 —— 和脚手架相反。
 */
export function addLevelOnTop(): AnyNodeId | null {
    const { nodes, addNode } = useScene.getState()
    const currentId = resolveCurrentLevelId(useEditor.getState().currentLevelId, nodes)
    if (currentId === null) return null

    const current = nodes[currentId]!
    const id = addNode({
        type: 'level',
        parentId: current.parentId,
        level: nextLevelOrdinal(current.parentId, nodes),
        height: DEFAULT_LEVEL_HEIGHT,
    })
    useEditor.getState().setCurrentLevel(id)
    return id
}

/** 往上 / 往下切一层。到头了什么都不做，返回 false。 */
export function switchLevel(direction: 1 | -1): boolean {
    const { nodes } = useScene.getState()
    const currentId = resolveCurrentLevelId(useEditor.getState().currentLevelId, nodes)
    const next = adjacentLevelId(currentId, nodes, direction)
    if (next === null) return false
    useEditor.getState().setCurrentLevel(next)
    return true
}

import type * as THREE from 'three'
import type { AnyNode, AnyNodeId } from '../../../core/schema/types'

export type LevelDisplayMode = 'current' | 'below' | 'above'

/** 灰显的下层用原透明度的几分之几。 */
export const GHOST_OPACITY = 0.25

/**
 * 隐藏的上层搬到这个图层。相机和射线默认都只看图层 0，所以搬走 = 既不画、也点不中。
 * 全 src/ 没有任何别的地方用 layers（grep 过），所以下面敢直接 set(0) / set(31)。
 */
export const HIDDEN_LEVEL_LAYER = 31

const GHOST_BACKUP = '__levelGhost'

type MaterialBackup = { transparent: boolean; opacity: number; depthWrite: boolean }

/**
 * 某一层相对于当前层应该怎么显示。按序数比，和对照仓库 LevelSystem 一样。
 *
 *   就是当前层 / 没有当前层     → current（什么都不藏）
 *   序数更低                    → below（灰显，仍然能点）
 *   序数更高                    → above（隐藏，而且点不中）
 *   同序数（别栋楼的同一层）    → current
 */
export function levelDisplayMode(
  levelId: AnyNodeId,
  currentId: AnyNodeId | null,
  nodes: Record<AnyNodeId, AnyNode>,
): LevelDisplayMode {
  if (currentId === null || levelId === currentId) return 'current'

  const level = nodes[levelId]
  const current = nodes[currentId]
  if (level?.type !== 'level' || current?.type !== 'level') return 'current'

  if (level.level < current.level) return 'below'
  if (level.level > current.level) return 'above'
  return 'current'
}

/**
 * 把一层的整棵子树切到某种显示模式。设计成【每帧调用】也是对的：
 * GeometrySystem 在节点变脏时会整个换掉子节点和材质，上一帧灰掉的材质可能已经被 dispose 了，
 * 新材质是不透明的原样 —— 所以不能只在「切层那一刻」写一次。
 *
 * 只动两样东西：layers 和材质的 transparent / opacity / depthWrite。
 * 【不碰 visible】：group 的 visible 是 ParametricNodeRenderer 的 React prop，
 * 两个写入者抢一个属性，谁赢取决于提交顺序。
 */
export function applyLevelDisplay(root: THREE.Object3D, mode: LevelDisplayMode): void {
  root.traverse((object) => {
    // ⚠ 隐藏必须靠图层，不能靠 visible = false：three 的 Raycaster 只看 layers，
    // Mesh.raycast 也不看 visible —— 只设 visible 的话，看不见的上层照样挡住鼠标，
    // 顶视图里点一层的墙，选中的是正上方那面看不见的二层墙。
    object.layers.set(mode === 'above' ? HIDDEN_LEVEL_LAYER : 0)

    const material = (object as Partial<THREE.Mesh>).material
    if (!material) return

    for (const m of Array.isArray(material) ? material : [material]) {
      if (mode === 'below') ghost(m)
      else restore(m)
    }
  })
}

function ghost(material: THREE.Material): void {
  const data = material.userData as { [GHOST_BACKUP]?: MaterialBackup }
  // 只在第一次灰掉时备份。窗玻璃本来就是半透明的（0.35），还原时必须回到 0.35 而不是 1。
  const backup = (data[GHOST_BACKUP] ??= {
    transparent: material.transparent,
    opacity: material.opacity,
    depthWrite: material.depthWrite,
  })

  setTransparent(material, true)
  material.opacity = backup.opacity * GHOST_OPACITY
  material.depthWrite = false
}

function restore(material: THREE.Material): void {
  const data = material.userData as { [GHOST_BACKUP]?: MaterialBackup }
  const backup = data[GHOST_BACKUP]
  if (!backup) return

  setTransparent(material, backup.transparent)
  material.opacity = backup.opacity
  material.depthWrite = backup.depthWrite
  delete data[GHOST_BACKUP]
}

function setTransparent(material: THREE.Material, value: boolean): void {
  if (material.transparent === value) return
  material.transparent = value
  // ⚠ three r185 把 transparent 编进了着色器：不透明材质带 #define OPAQUE，
  // 片元里 diffuseColor.a 被钉死为 1.0（three.module.js 的 opaque_fragment）。
  // 渲染器只在 material.version 变了才重新选程序 —— 不置 needsUpdate 的话，
  // 材质进了透明队列、opacity 也改了，画出来却仍然是【完全不透明】的。
  // 只在真的切换时置位：每帧都置位等于每帧重新求一次程序缓存键。
  material.needsUpdate = true
}

 * 当前层实心、下层灰显、上层隐藏。
 *
 * 在 app 层而不是 viewer 层：「当前层是哪一层」是编辑体验，D4 不许 viewer 知道。
 * 📌 sceneRegistry.byType 从 M1 记到现在的「有写入无读者」，这里是第一个读者。

 * 每帧跑，理由见 applyLevelDisplay 的注释（GeometrySystem 会换掉材质）。
 * 挂在 <Viewer> 的 children 里，所以它的 useFrame 订阅晚于 Viewer 内部的 GeometrySystem ——
 * 同优先级按订阅顺序执行 ⟹ 同一帧里几何先重建、这里后覆盖，新材质不会实心闪一帧。
 */
export function LevelVisibility(): null {
  // ⚠ 不要写成 useFrame(cb, 5)。对照仓库的 LevelSystem 用的是 priority 5，
  // 但 R3F 9.7.0 里任何 priority > 0 的订阅都会让 internal.priority 自增、关掉自动渲染
  // （events-*.cjs.dev.js:1146 / :16196）。它有自己的渲染循环，我们没有 —— 抄过来画面全黑。
  useFrame(() => {
    const levelIds = sceneRegistry.byType.level
    if (!levelIds || levelIds.size === 0) return

    const { nodes } = useScene.getState()
    const currentId = resolveCurrentLevelId(useEditor.getState().currentLevelId, nodes)

    for (const id of levelIds) {
      const object = sceneRegistry.nodes.get(id)
      if (object) applyLevelDisplay(object, levelDisplayMode(id, currentId, nodes))
    }
  })

  return null
}

/**
 * 把「平的」场景（墙 / 楼板直接躺在 rootNodeIds 里，M8 之前的样子）包进
 * Site → Building → Level 0。已经有容器就原样返回。
 *
 * ⚠ 这【不是】数据迁移 —— 这个项目现在没有任何持久化，没有语料可迁。
 * 真正发生的语义迁移在代码里（批 F：wall.height 从「高度」变成「显式高度」）。
 * 这个函数的两个真实用途：开机脚手架的兜底，以及 M9 迁移链的第一个节点 ——
 * 趁还没有存档格式，先把形状定下来。ROADMAP 那句「第一次真实 schema 迁移」
 * 按工作约定第 6 条在 §02 K 已经更正过。
 *
 * 纯函数：不碰 store，不改入参。
 *
 * ⚠ 它绕过 addNode 直接拼 nodes，所以【children 这个反规范化索引要自己维护对】。
 * STATE.md 里挂在 M9 的那条债（「存档导入若直接写 nodes，必须重建这个索引，
 * 否则门渲染不出来且不报错」）—— 这个函数是它的第一个当事人。
 */
export function migrateToLevels(snapshot: SceneSnapshot): SceneSnapshot {
  const migrated = Object.values(snapshot.nodes).some(
    (n) => n.type === 'site' || n.type === 'building' || n.type === 'level',
  )
  // 只要已经有任意一种容器就不动 —— 半套脚手架（有 building 没 level）
  // 再补一套会变成两个 site，比不迁更糟。
  if (migrated) return snapshot

  const site = SiteNode.parse({ type: 'site' })
  const building = BuildingNode.parse({ type: 'building', parentId: site.id })
  const level = LevelNode.parse({
    type: 'level',
    parentId: building.id,
    level: 0,
    // 创建处显式写 height：缺席要留给「用户没设过」这个语义。
    height: DEFAULT_LEVEL_HEIGHT,
  })

  const adopted = snapshot.rootNodeIds.filter((id) => snapshot.nodes[id] !== undefined)

  const nodes: Record<AnyNodeId, AnyNode> = { ...snapshot.nodes }
  for (const id of adopted) {
    // 展开只复制自有 key：wall.height 不在的仍然不在（plane-bound 语义保住）。
    nodes[id] = { ...nodes[id]!, parentId: level.id } as AnyNode
  }

  nodes[site.id] = { ...site, children: [building.id] }
  nodes[building.id] = { ...building, children: [level.id] }
  nodes[level.id] = { ...level, children: [...adopted] }

  return { nodes, rootNodeIds: [site.id] }
}
