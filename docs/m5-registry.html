这一次的「最常见错误做法」和 M3 不一样

"For registry-driven kinds, prefer no per-kind system. If your kind's only job is 'rebuild geometry on dirty', set def.geometry and let the framework's <GeometrySystem> handle the rebuild loop. Per-kind systems remain for extra responsibilities."

④

抽不变量

node-definitions.md 末尾有一节叫 ## Rules， 规格书自己抽好了六条；后面还有一节 ## Pitfalls， 四条各配一段「症状」。照抄，然后砍掉依赖我们范围外功能的。

留下的（M5 范围内）

① Builders must be pure.
   def.geometry 里不许 import useScene。要读别的节点，走 ctx。

② Builders emit local-space children.
   渲染器拥有 transform，builder 产出的顶点当作父节点在原点。
   永远不许把世界坐标烘进顶点。

③ One mesh registered per node ID.
   通用渲染器每个节点注册一个 <group>。

④ Custom systems 是叠加，不是替代。
   def.geometry + def.system 同时存在时两个都跑。

⑤ Dispose on rebuild.
   换子节点前必须 dispose 上一批的 geometry 和 material。

⑥ def.renderer 覆盖通用渲染器。
   设了它就自己拥有挂载；但 def.geometry 仍然会跑
   —— 自定义渲染器可以注册一个空 group 让系统来填。

两条 Pitfall 直接变成验收项

Pitfall 1 —— 系统不许 mutate group.position / rotation

ParametricNodeRenderer 用 JSX 绑定 <group position={…}>。React 只在底层值变化时才重新应用这个 prop。 如果几何系统在重建之后命令式地把 group.position 归零， R3F 没有理由在下一帧重新渲染，group 就永远停在原点了。

症状：节点每次几何重建就跳回 (0,0,0)。 规格书说这正是旧的 per-kind 系统干过的事。

Pitfall 2 —— builder 产出的子节点必须打 userData.__fromGeometry

一个注册的 <group> 会同时挂两种子节点： builder 造的网格，和 React 渲染的宿主子节点。 重建时只许 dispose 前者。

症状：把一个物件拖到宿主上，物件消失且再也不回来。 M5 还没有宿主（M7 才有门窗），但这一条现在做只要三行，M7 补做要重新理解整个 dispose 路径。

不变量 ① 是本次最大的测试红利

D11 说「React/渲染层不测，靠跑起来看」。 而不变量 ① 把几何生成从渲染层里挖了出来—— buildWallGeometry(node, ctx) 是个纯函数， 输入是数据、输出是 Object3D， 不需要 React、不需要画布、不需要 GPU。

它 import 了 three，所以跑不了 D11 说的「Node 里裸跑」——但 three 在 Node 里 能构造几何，只是不能渲染。 new THREE.ExtrudeGeometry(...).attributes.position.count 在 vitest 里是可以断言的。 你写 §05 时值得考虑把这条算进去。

⑤

切最薄的垂直片

ROADMAP.md 给的切法是「把 wall 迁进注册表（第一个用户）， wall-renderer.tsx 删除」。

这里有一个真实的张力，你写 §01 时必须正面回答

DECISIONS.md D10 写着：「M1–M4 硬编码 switch (node.type)，M5 加第三种类型时才抽 nodeRegistry。 rule of three。」

而 M5 结束时你只有一种类型（wall）。第二、三种（slab / ceiling / column） 在 M6。也就是说 —— 按 D10 的字面意思，M5 现在做注册表是早了两个类型。

我不替你回答。但可以给你三个可查证的事实： ① M6 的验收原文是「加第三种类型的工作量 ≈ 加第二种，这一条本身就是对 M5 的检验」—— 说明 ROADMAP 早就知道 M5 先于用户出现； ② 对照仓库的迁移是 Phase 1–6，第一批迁的也只有一种类型（shelf）； ③ M4 的 dirtyNodes 现在零消费者， 它是为 GeometrySystem 建的。

怎么判断一个切法够不够薄

M3 那次用的判据，这次仍然适用：

  • 切完之后能跑起来看见东西吗？不能的话，切太薄了（只建了类型没建实现）。
  • 切完之后有东西被删掉吗？没有的话，切太厚了或者方向错了—— 注册表的价值是消除代码，不是增加一层。M5 必须让 wall-renderer.tsx 和 node-renderer.tsx 里的 switch 死掉。
  • 下一个里程碑能不能零改动接上？M6 加三种类型时， 如果还要动 M5 建的任何一个框架文件，说明抽象抽错了位置。

第二条是这次的关键。M5 是十四个里程碑里唯一一个 净删除行数可能为正的。如果你算完发现新增远多于删除， 大概率是把 M6/M7 的东西提前做了。

悬而未决的三处 —— 这三个是 §02 的主要内容

?1

AnyNode 还手写 discriminatedUnion 吗

你现在是：

// core/schema/types.ts
export const AnyNode = z.discriminatedUnion('type', [WallNode])

加一种类型要改这一行。注册表的诱惑是让 AnyNode 从 nodeRegistry.schemas() 推出来（对照仓库有这个方法）。

但那是运行时的值，而 AnyNode 是编译期的类型。 useScene.getState().nodes[id] 要能收窄成 WallNode， 靠的是静态联合，不是 Map 里有什么。 对照仓库 schemas() 的返回类型是 ZodObject<any>[] —— any，它放弃了这条路。你怎么处理，写进 §02。

?2

斜接走 ctx 还是 computeLevelData

墙的几何依赖邻墙。M4 里你的解法是 MiterContext（React context）+ level-miter-cache。 注册表模型下有两条路：

  • ctx.siblings —— 规格书原文说 "Wall — ctx.siblings for corner mitering with adjacent walls"。每个墙自己算一遍。 O(N²)，但简单。
  • def.computeLevelData —— "Called once per level per frame, before the per-node def.geometry calls… wall: calculateLevelMiters(walls) — every wall's mesh reads its junctions from the level-wide miter graph." 这就是你 level-miter-cache.ts 的注册表版本，一比一对应。

规格书里还有一句直接相关的："For level-scoped batch data (wall mitering across an entire level), ctx can be extended with ctx.levelData?.miters in a future revision — decided alongside the wall migration." 它们也是在迁 wall 的时候才决定的。

?3

什么时候注册

nodeRegistry 是模块级单例。wallDefinition 什么时候进去？

  • import 副作用：definition.ts 末尾直接 registerNode(wallDefinition)。省事，但谁 import 它？ 没人 import 就没注册，而 tree-shaking 会帮倒忙。
  • 显式 registerAllNodes()：在 main.tsx 调一次。 清楚，但每个测试文件也得调，忘了就是「注册表是空的」。

对照仓库两条都用了（_register 私有 + registerNode 公开 + _reset 测试专用）。注意它有个 _reset()「Test-only — 不从包的 barrel 导出」 —— 那是为了让测试之间不互相污染。你的 §04 建造顺序里要给它留位置。
