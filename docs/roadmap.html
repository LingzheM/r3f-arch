01目标为什么改了

「90% 功能覆盖」不是难，是不存在

你最初说的目标是「功能和 UI 达到原项目 90%」。我重新量了规模：

项量含义
节点类型46 种含风管三通、冷媒管、屋顶涡轮通风器、电梯井、点云扫描
专属面板 / 工具24 / 32每种类型一套
packages/nodes160k 行730 文件
editor UI90k 行272 文件，含 2D 平面图 UI 13.6k 行
全项目390k 行≈ 2 人年全职

按每小时 100 行可用代码算（对几何/交互代码已经算快），390k 行 ≈ 3900 小时。 我生成代码能压缩打字时间，压缩不了三维几何的调试时间—— M2 那三个深坑就是样本，每一个都是"看起来对但只在特定角度错"。

所以目标改成完整产品：不追覆盖率，追一个闭环。 画多层住宅、开门窗、盖屋顶、上颜色、能存能读，有侧栏有属性面板。 功能上是原项目的 25–30%，但它是完整的。

04质量能保证到什么程度

「完美衔接」做不到，但漂移可以被抓住

这三件事一定会发生，问题只是被不被发现

① 接口漂移。后一个 M 的计划假设前一个 M 留了某个钩子，实际写法不同。 已经发生过一次——我给的 eslint 配置把 allowTypeImports 放在了顶层， 正确位置是每条 paths 条目内部。你自己改对了；如果你没告诉我， 我后面所有计划都会建立在一份和你代码不一致的想象上。

② 决策失忆。跨对话必然发生。我不记得当初为什么选 A 不选 B， 新计划和旧决策打架。对策是 DECISIONS.md ——13 条，每条都带"为什么"。

③ 累积腐坏。最致命。前 5 个 M 的临时方案在 M9 集中爆发。 对策是每个 M 的"故意保留的缺陷"清单标注到期 M， 汇总在 STATE.md 里跟踪——现在有 8 条未偿。

唯一可靠的锚是第 2 步：每个 M 开始前读你的真实代码。 计划文档会过期，决策记录会遗漏，只有代码不会撒谎。 这也是为什么你的项目和对照仓库在同一个 workspace 下很重要—— ../editor 我随时能读，不需要你贴源码给我。

你这边要做的三件事

  1. 每个 M 验收后更新 STATE.md（或者让我更新）。这是唯一需要你维护的东西。
  2. 改了我给的代码就说一声。不用解释为什么，说"我把 X 改成 Y 了"就够——我会更新文档并检查下游影响。
  3. 每个 M 结束打个 git tag（m3-done 之类）。M10 出跨模块 bug 时，能二分定位到是哪个 M 引入的。
