B1

版本号放在文档上，还是每种节点一个

推荐：文档级整数

对照仓库选的是后者：每个 NodeDefinition 一个 schemaVersion（wall 是 7、door 是 2）。 但 registry.ts:54 只校验它是正整数，加载路径上没有任何人读它， wiki/architecture/node-schemas.md:87 原文：「reserved for future use；today all load-time migration is centralised in migrateNodes」。

推荐文档级的三个理由：① v0 → v1 要把所有类型收进容器，对照仓库的电梯迁移要改层的 children—— 跨类型的迁移不属于任何一个类型；② 按类型编号会变成 N 维兼容矩阵，一个文档没有单一「版本」； ③ 按类型编号真正的用户是插件（各管各的节点），而我们明确不做插件（D2）。

选它的代价：任何一种节点的 schema 变了，整个文档版本号 +1，其它类型的节点白走一遍迁移链（它们那一环是恒等函数）。 可以接受：迁移只在加载时跑一次。

B2

导入 JSON：新建一个场景，还是覆盖当前场景

推荐：新建

新建：导入永远不销毁任何东西，不需要「确定要覆盖吗」，也不需要把替换做成可撤销的一步。 代价是导入十次得到十个场景，列表要自己清理。

覆盖：符合「打开文件」的直觉，但它是 M9 里唯一一个会销毁数据的操作， 而且要和自动保存的顺序打交道（§02 F 的第二条顺序）。我不建议在第一版就引入一条会销毁数据的路径。

B3

要不要抄对照仓库的「疑似误删」护栏

推荐：不抄，靠存档点

对照仓库 use-auto-save.ts 有一条 isSuspiciousNodeDrop：节点数从「有内容」掉到「只剩脚手架」时拒绝写盘， 注释写的是「an accidental full deletion far more often than an intent」。 （它是随一次功能 PR 进去的，不是某次事故的修复——我查了 git log，没有证据说它救过什么。）

不抄的理由：它会让「我真的想清空这个场景」变成一个静默失败的操作——你清空、刷新、东西又回来了，而且没人告诉你为什么。 我们有更直接的安全网：Ctrl+S 存档点（每场景 10 个），而且刷新之后撤销栈本来就是空的，所以「撤到底再刷新」这条路径没法把存档冲掉。 如果你更怕误删，那就抄它——十行纯函数、可测，代价是那个静默失败。

B4

M4 那笔「live 覆盖无按类型校验」的债，还到哪一步

推荐：只还写入边界

还写入边界（updateNode 里校验合并结果，§02 I）：把「错字段能进 store」挡在落盘之前。 原型里已经写出来跑过，5 条测试、2 个变异体全被抓。

B5

③ 量成本，决定手写还是抄

候选一：zustand 自带的 persist 中间件（5.0.15，esm/middleware.mjs）。它确实有版本化： version（:334、:362）和 migrate(persistedState, version)（:392-404）。不用它，四个理由：

  1. migrate 是一个函数拿到「旧状态 + 旧版本号」，链要你自己在里面写 switch——而链本身正是 ROADMAP 要的东西（「每次 schema 变更追加一个迁移函数 + 一个测试」）。
  2. 它把一个 store 持久化到一个键。我们要的是「一个索引 + 每场景一个文档 + 存档点」，形状不匹配。
  3. 它的 hydrate 走 setState，而我们的读档必须同时做三件它不做的事：清 zundo 历史、换脏集、清掉指向旧场景的编辑器 id（§02 E）。
  4. 导入 / 导出要走同一条加载管线。用中间件的话，文件那条路得再写一遍解析 + 迁移 + 规范化。

候选二：照抄对照仓库的 migrateNodes（945 行文件里迁移相关约 340 行）。它是「没有版本号」那个世界的产物—— 抄它等于把 ② 的四条毛病一起抄过来。抄的是它的经验，不是它的代码。

手写量（原型实测）：core 实现约 500 行 + 语料 57 行，测试约 560 行。 这个量级里没有一行是「框架」，全是本项目的规则：容器怎么包、children 怎么重建、缺席怎么保住。

一处「抄形状」：SceneStorage 的方法名照对照仓库 packages/mcp/src/storage/types.ts:121-132 的 SceneStore（save / load / list / delete / rename）。将来真接服务器时，换的是实现，不是调用点的名字。

变异测试跑到一半被打断，把两个源文件写成了全 NUL 字节——handoff-m9.md ⑦ 记的是「原子写（临时文件 + os.replace）」， 这不够：NTFS 上元数据先落盘、数据后落盘，进程被杀时文件长度对、内容全是零。必须 f.flush() + os.fsync() 之后再 os.replace。

而且同一次打断把备份也清零了（备份是同一个进程刚写的）。所以备份不能只是「放在 src/ 之外」， 还得在另一个时间点、由另一条命令做——现在是跑变异前先 tar 整个 src/。 最后能恢复，靠的是这两个文件的原文还在会话里，以及仓库那份 use-scene.ts 干净（我从来没动 src/）。

A · 文档长什么样

{
  "format": "r3f-arch/scene",
  "version": 1,

  • format 把「我们的文档」和「随便一个带 nodes 的 JSON」分开。没有它，任何 { nodes: {} } 都会被当成 v0（§06 有一条就是这个口子）。
  • nodes 是数组而不是 Record：key 本来就是 id，数组整个消灭「key 和 id 对不上」这一类错（m6-prep.md:71 的理由，照用）。
  • 不存视图状态：currentLevelId / selectId / viewMode / 相机都不进文档。它们属于「谁在看」，不属于「房子是什么」。
  • 场景名和时间戳不进文档，进索引（G）。导出文件额外带一个 name，加载器不认识它也不在乎。

B · 版本号放在文档上，迁移链按版本号跑

  2. 链上流的是没 parse 过的 RawNode。parse 会剥掉老字段（D28：删字段 = 静默丢数据）、填上今天的默认值——两件事都必须等迁移做完。全链结束后统一 parse 一次（D）。
  3. v0 是全链唯一允许「看形状」的地方——它就是版本号出现之前的数据，没有别的信息可看。从 v1 起一律看版本号。

为什么非要版本号 —— 一个数、两种意义：

文档楼板 elevation它是什么该怎么办
v0（M6 / M7 时代存的）0.05当年的 DEFAULT_SLAB_ELEVATION，被 .default() 物化进数据改成 0

只看数据，这两行分不出来。形状嗅探在这里只有两个选择：要么把人设的 0.05 也改掉，要么让老数据永远陷进楼板 5 cm。 版本号就是那一列额外的信息。（原型里「按数值嗅探」这个变异体红 2 条，就是这条的护栏。）

为什么是文档级而不是按类型：v0 → v1 要把所有类型的节点收进容器，对照仓库的电梯迁移要改层的 children—— 跨类型的迁移不属于任何一个类型；按类型编号会变成 N 维兼容矩阵。详见前置 B1。

C · 第一环 v0 → v1：M8 之前的平场景

两件事，都只在「平」的时候做（一个容器都没有 = M8 之前）：

  1. 楼板 elevation === 0.05 → 0（§00 ⑥ 第 1 条）。
  2. 收进 Site → Building → Level 0：直接调 migrateToLevels（D27）——它只读 type、按 id 查存在、展开复制，所以 raw 节点过得去。 这是它从 M8 起等着的那个位置。根用 deriveRootIds 按 parentId 推，不信存档里的 rootNodeIds。

「有容器但没版本号」怎么办？——比如 M8 期间从控制台 JSON.stringify 出来的场景。它仍按 v0 读，但不再包一层、也不改楼板： 「平」才是 M8 之前的标志；有容器的场景里出现 0.05，只能是人设的。原型里有一条测试专门钉这个（「去掉『平』判据」这个变异体红 1 条）。

不迁的两件事，写下来别装作没想过： ① v0 天花的 height 缺席——M6 时它的意思是「2.5 常量」，今天是「层高 − 0.01」，默认层高下差 1 cm；而 M6 的本意就是「贴墙顶」，缺席在今天的语义里正好对，不迁。 ② v0 墙的 height 缺席——M1–M7 是 2.5 常量，今天跟层高，而新建的 Level 0 层高正是 2.5，等价，不迁。

normalizeSceneNodes 是进 store 前的最后一道，它就是 STATE.md 那笔「导入必须重建 children」的债的还法：

  • parentId 是真相，children 是索引（D19）。按 parentId 重建 children，存档里的 children 只用来保顺序。
  • 根按 parentId === null 推，存档里的 rootNodeIds 只用来排序。
  • 逐个 safeParse；坏节点 · 重复 id · 父不存在 · parentId 成环 · 祖先被丢——丢掉，但每一个都进 LoadReport，UI 要显示（「读档：丢弃 2 个节点」）。

对照仓库 setScene 做同样的事（删孤儿、删不可达，use-scene.ts:1217-1240），但只 console.warn。用户不看控制台。 「静默」正是本项目八个 bug 的共同点，所以这里坚持把报告交到 UI。

E · 进 store：replaceScene

读档、切场景、导入都走同一个函数。三件事缺一不可：

  1. 一次 setState 写完，脏集换成「恰好是新场景全部节点」的新 Set。 对照仓库吃过「分两步写」的亏：半规范化的中间态和读档前的空场景都变成了撤销目标（use-scene.ts:1242-1245）。
  2. 历史清空——读档不能被 Ctrl+Z 撤回到上一个场景。
  3. 清掉指向旧场景的编辑器 id（selectId / currentLevelId，在 app 层做，见 J）。

viewer 一行不改，读代码确认过：NodeRenderer 找不到节点返回 null（node-renderer.tsx:18）； GeometrySystem 遇到不存在的脏 id 直接 clearDirty（geometry-system.tsx:35-37），group 还没挂上就留到下一帧（:47-49）。

不拿暂停租约。我原本照 ensureScaffold 的样子写了 acquireSceneHistoryPause， 但变异测试证明它不产生任何可观察差别（紧跟着的 clear() 已经把那条记录清了，去掉租约 268 条全绿）。删掉了——少一个依赖，少一条要靠自觉记住的规矩。

F · 自动保存

  • 只认 nodes / rootNodeIds 换了引用。脏集是就地改的、live 覆盖不碰 store——拖拽期间一次都不触发。撤销 / 重做算改动，会存。
  • 防抖 500 ms（m6-prep 300，对照仓库 1000）；pagehide 立刻 flush——对照仓库的注释说得清楚：刷新得快，最后一次改动就没了。
  • 写失败要看得见。状态栏显示 已保存 / 未保存 / 保存失败；失败时改动保持「脏」，下一次改动或 flush 重试。 m6-prep 把失败全吞了（:85-87）——配额满时用户永远不知道。
两条顺序，错了都是静默改坏数据 —— 原型两条测试各钉一个方向

① 启动：先读档，后启动自动保存。反过来，读档那一次 setState 自己会被当成改动写一次盘。 原型里有一条故意把顺序写反的测试，它确实写了一次。对照仓库在这上面也栽过（hook 挂载早于读档，防误删基线恒为 0，use-auto-save.ts:18-23）。

② 切场景：先 stop()（把挂着的改动写进旧场景），再 replaceScene，再为新场景 start。 反过来：replaceScene 让 nodes 换引用 → 旧的自动保存把它当成改动 → stop() 那次 flush 把新场景的内容写进旧场景的 id。不报错、不闪，下次打开旧场景才发现它变成了别的房子。 这是 M9 里最危险的一个 bug，原型测试把两个方向都写下来了。

G · 存储：一个索引 + 每场景一个键

r3f-arch:index                 { scenes: SceneMeta[], checkpoints: CheckpointMeta[], currentSceneId }
r3f-arch:scene:<sceneId>       SceneDocument
r3f-arch:checkpoint:<cpId>     SceneDocument
  • 索引是缓存，文档才是真相。索引丢了或坏了，扫 scene:* 键重建（名字退化成 id）。所以 KeyValueStore 需要一个 keys()。
  • 先写文档，再写索引。配额满时挂的是大的那个（文档），索引保持旧值、仍然自洽；反过来索引会指向一个没写成的文档。
  • 降级保护：SceneMeta.docVersion 记着文档是哪个版本存的。比当前代码新 → save 抛 SceneTooNewError，load 报 too-new。 这在本项目是真实场景：你会 git checkout 老提交对照着看，老代码打开新存档，自动保存会用旧格式覆盖它。
  • 存档点是整份文档的拷贝，每场景留最近 10 个，旧的连文档一起删。
  • 同步接口（前置 B5）：localStorage 本身同步。

I · 写入边界校验：M4 那笔债在 M9 到期的真正原因

STATE.md：「live 覆盖是 Partial<AnyNode>，无 per-type 校验 → M9」。为什么偏偏是 M9？ 因为从 M9 起，store 里的东西会被写进磁盘。Partial<AnyNode> 按联合分配—— updateNode(wallId, { polygon: … }) 类型检查通过，mergeNodePath 的 as AnyNode 把它放进 store； 以前刷新就没了，现在它落盘，下次读档整堵墙作为 invalid 被丢掉。

更正（2026-09-16，工作约定第 6 条，沙箱探针实测）：上面这个例子写错了

原文说「updateNode(墙, { polygon }) 落盘后，下次读档整堵墙作为 invalid 被丢掉」。不对。z.object 默认剥掉不认识的键，parse 成功，polygon 被静默去掉，墙完好无损（探针：parseSuccess = true，polygonKept = false）。

真正会在读档时丢数据的是值不合法的 patch。最现实的例子就在前置 C · C5 的演示步骤里：控制台 updateNode(屋顶层id, { height: 0 })（本想写 1.0）。LevelNode.height 是 .positive()，今天的 updateNode 照样把它放进 store，画面上那一层只是变扁；自动保存把它写盘；下次读档，层 invalid → 这一层的墙和楼板 missing-parent → 墙上的门窗 ancestor-dropped → 整层消失，只剩 site 和 building（探针对 M7 语料实测）。

所以写入边界的两个检查，理由要分开写：safeParse 挡的是「会让读档丢掉整层」的非法值（§04 第 08 步的「负厚度」测试就是这一类）；「parse 剥掉了哪些键」挡的是「调用方以为自己在改别的类型」——它不丢数据，但静默剥掉会把一个调用方的 bug 藏起来。两个检查都保留，决定不变，改的是理由。

还法（前置 B4）：在 updateNode 里校验合并结果——先查 type / id 没变，再 AnyNode.safeParse， 再查「parse 剥掉了哪些键」（剥掉的就是别的类型的字段），校验通过才 set。 addNode 早就在 parse（use-scene.ts:65），这一步只是让两个写入口对齐。

它不还的那一半：live 覆盖本身仍是 Partial<AnyNode>，拖拽预览期间仍无校验——但它不落盘、松手就清，最坏画错一帧 → M13。 D23 的回归必须测：height: undefined 删掉的键，不能被 parse 填回来（height 没有 .default()，所以不会，但要有测试钉住）。

hint，四步：

  1. 逐个 AnyNode.safeParse。失败记 invalid（id 不是字符串就记 null）；id 出现过记 duplicate-id，留第一个。
  2. 给每个节点下判决：沿 parentId 往上走，带「本次路径」集合 + 全局判决缓存。 碰到缓存 → 整条路径跟它（它不 ok 就全是 ancestor-dropped）；碰到路径里已有的 id → 成环，环上记 cycle、挂在环下面的记 ancestor-dropped； 父不存在 → 最上面那个记 missing-parent、下面的记 ancestor-dropped。 缓存让它线性，路径集合让它不死循环（没有路径集合，环会把它挂住，不是报错而是卡死）。
  3. 重建 children：先按存档顺序保留「确实以我为父」的，再追加漏掉的；和原来不同就换掉并记进 repairedParents。
  4. 根 = deriveRootIds。
