01这一步解决什么问题

一处代码线性增长，加每个类型付一次固定成本

你现在的代码里有 18 处提到 'wall'，散在 11 个文件。 但它们不是一回事，混在一起看会得出错误结论。分成三类：

A · 分发点 —— 一处代码，随类型数线性增长

// viewer/components/node-renderer.tsx:25
switch (node.type) {
    case 'wall':
        return <WallRenderer node={node} />
    default: return null
}

加 slab 就多一个 case，加 column 再多一个。M6 一口气加三种，这里变成四个 case。 这是最容易看见的那种痛，但它其实是两类里比较轻的一类—— 一个 switch 长到 48 个 case 也只是难看，不会错。

B · 样板 —— 每个类型各付一次固定成本

wall-renderer.tsx 55 行。把它逐行分类：

行做什么换成 slab 要改吗
16–17useRef + useRegistry(id, 'wall', ref)只改字符串
14useEffectiveNode(documentNode)不改
24useNodeEvents(node, 'wall')只改字符串
21–22读 SelectionContext，算 isSelected不改
26–29useMemo 建几何 + 依赖数组依赖数组要按字段重列
31useEffect dispose不改
33–36useMemo 算 transform不改（但 slab 没有 transform）
44–58<mesh> + 材质不改
真正 wall-specific 的：buildWallGeometry(node, miter) 一行 + 两个颜色常量。

55 行里 52 行是样板。M6 加三种类型 = 复制粘贴三遍这 52 行， 而且每一遍都有机会把 useMemo 的依赖数组抄错 —— 抄错的表现是「改了参数几何不更新」，而它不产生任何红字。

C · 真·类型特有 —— 不该消灭

wall-linking.ts:14 筛墙算邻接、wall-tool.tsx 画墙、 use-editor.ts 的 Tool 联合 —— 这些本来就该按类型分。 注册表不该碰它们，碰了就是过度抽象。

A 和 B 分开，是这一节唯一要说清楚的事。 它们靠不同的东西解决：A 靠查表（一个 Map 取代 switch）， B 靠通用渲染器（一份代码取代 N 份复制）。

规格书把这两件事分给了两个组件： <NodeRenderer> 治 A，<ParametricNodeRenderer> 治 B。 读源码时如果觉得「为什么要两个渲染器组件」，答案在这里。

为什么是现在，而不是 M6 之后 —— 正面回答 D10

D10 写的是「M1–M4 硬编码 switch，M5 加第三种类型时才抽注册表。 rule of three」。而 M5 结束时只有 wall 一种。按字面意思，现在做早了两个类型。

三条理由，按份量排：

  1. rule of three 数的是「第三次重复」，不是「第三个类型」。 M6 的验收原文是「加第三种类型的工作量 ≈ 加第二种，这一条本身就是对 M5 的检验」—— 如果 M5 之后再抽，M6 就没有可检验的东西了，你只能事后说「好像是快了点」。 先建再验证，和先重复三遍再抽，得到的是同一份代码，但只有前者能验收。
  2. M4 已经把地基建好了，而且它现在零消费者。 useScene.dirtyNodes 是 M4 建的，GeometrySystem 是它的第一个用户； sceneRegistry.byType 有写入无读者。 地基放着不用会腐坏——M4 §08 B 组第 09 条（updateNode 没接脏标记） 就是它腐坏的第一个证据：没人消费，所以没人发现它是错的。
  3. M6 的三种类型不是「三次重复」，是「一次×3」。 slab / ceiling / column 会在同一个时间段写完。 如果 M5 不做，M6 就是「复制粘贴三遍 52 行样板，然后立刻回头抽掉」—— 那不是 rule of three，那是明知故犯。

D10 不需要推翻，需要补一句限定： 「rule of three 数的是重复次数。当 N 个用户会在同一个里程碑内一起出现时， 提前抽象不算违反——因为『三次重复』根本不会分三次发生。」 这一句值得追加成 DECISIONS.md 的一条新决策（不改 D10，引用它）。

02机制说明

三个字段、两个组件、三处分叉的决定

三复选框：没有判别标签，「声明即参与」

规格书原话是 "There is no discriminator tag — presence is participation"。

geometryrenderer谁挂载谁填几何例
✓—ParametricNodeRendererGeometrySystem wall（M5）、slab / column（M6）
—✓你的组件你的组件GLB 家具、<Html> 标注（本项目不做）
✓✓你的组件GeometrySystem自定义挂载 + 参数化几何
——无无纯结构节点（M8 的 site / building / level）

为什么不用一个 kind: 'parametric' | 'custom' 的标签？ 因为第三行和第四行都存在。标签只能表达互斥，而这三个字段是正交的。 用标签的话，第三行要发明一个 'custom-parametric'， 第四行要发明一个 'none'—— 而每发明一个标签值，所有消费点都要多一个分支。 这正好是注册表要消灭的那种东西，在注册表内部复现一遍就荒唐了。

两个组件的分工

NodeRenderer（39 行）—— 治「分发点」
  查表 → def.renderer ? 用它 : def.geometry ? 通用渲染器 : 不渲染
  加多少类型都不改这个文件

ParametricNodeRenderer（44 行）—— 治「样板」
  空 group + useRegistry + useNodeEvents + 标脏
  每个参数化类型共用这一份

GeometrySystem（134 行）—— 每帧的重建循环
  脏集 → computeLevelData（每类一次）→ def.geometry（每节点一次）
       → dispose 旧子节点 → 挂新子节点 → clearDirty

三处分叉的决定

?1

定义放哪层

选了候选甲

NodeDefinition 类型放 core/registry/， 用 import type * as THREE from 'three'—— 编译后整行消失，是 D4 已记录在案的例外， eslint.config.js 的 allowTypeImports: true 已放行。 对照仓库 core/src/registry/types.ts:2 一字不差地这么写。

定义实例（wallDefinition）和 builder 放 viewer/nodes/wall/——它们要 new THREE.ExtrudeGeometry()，是运行时依赖。

为什么不加第四层：

  • D4 的「三层」是写进 DECISIONS 的，推翻它要付一条新决策 + 一条 eslint 规则 + 一次目录搬迁， 而买到的只是「schema 和 definition 在同一个目录里」。
  • 对照仓库需要 packages/nodes 是因为它有 48 种类型， 每种十几个文件（tool / panel / paint / floorplan / preview …）。我们有 8 种，每种 2 个文件。
  • 这个决定是可逆的。真到 M12/M13 觉得挤，把 viewer/nodes/ 整个 git mv 成 src/nodes/ 加一条 lint 规则就行。 现在做则要为一个还没发生的问题付代价。

放弃的那条会怎样：选丙（core 存定义、viewer 注入几何）的话， wallDefinition 变成分两次拼起来的对象， 「什么时候拼完」成了隐式依赖 —— 而 M9 读档时机、测试初始化都会踩它。

?2

AnyNode 继续手写 discriminatedUnion

不变

诱惑是让它从 nodeRegistry 推出来。不行，而且理由是根本性的： 注册表是运行时的值，AnyNode 是编译期的类型。 

// 这一行之所以能收窄成 WallNode：
if (node.type === 'wall') node.start   // ✓ 静态联合

// 如果 AnyNode 从 Map 推导，编译器不知道 Map 里有什么，
// 收窄就没了 —— 而收窄是这个项目里最常用的一件事。

对照仓库自己也放弃了这条路。它的 nodeRegistry.schemas() 返回类型是 ZodObject<any>[]—— any。那个 any 就是它放弃的痕迹。 代价是加类型要改 core/schema/types.ts 一行， 而那一行改不改编译器会告诉你——属于「遗漏」里最良性的一种。

?3

斜接走 def.computeLevelData

删掉两个文件

ctx.siblings 让每堵墙自己算一遍整层交点图 —— O(N²)， 拖一堵墙时每个邻居各算一次完整的斜接。不选。

computeLevelData 每帧每类跑一次，产物落进 ctx.levelData。 它和你 M4 写的 level-miter-cache.ts 一比一对应， 规格书原文："wall: calculateLevelMiters(walls) — every wall's mesh reads its junctions from the level-wide miter graph."

这个选择顺手删掉了 M4 的缓存

level-miter-cache.ts（33 行代码 + 14 个测试）在 M5 里整个消失。 不是因为它写得不好，是因为它解决的问题被换了个位置解决：

  • M4 的缓存挡的是「React 因为别的原因重渲染 → useMemo 重跑 → 全场重算」。
  • M5 的 GeometrySystem 第一行就是 if (dirtyNodes.size === 0) return—— 空闲帧根本不进循环，没有可缓存的东西。

拖拽时呢？每帧都有脏节点，computeLevelData 每帧跑一次全量斜接。 而 M4 的缓存在拖拽时也每帧未命中（输入真的在变）。成本完全一样。

连带删掉的还有 MiterContext 和 use-level-miters.ts—— 斜接不再需要一条穿过 React 树的通道。

一处对规格书的**故意偏离**：墙的 transform 由 builder 算

Rule ② 说「渲染器拥有 transform」，我们做不到

规格书的 ParametricNodeRenderer 写的是 <group position={node.position}>——它假设每种类型都有 position 字段。 我们的 WallNode 没有：它由 start / end 两个点定义（D3），中心和朝向是导出量。

通用渲染器不知道怎么从 start/end 推 transform，也不该知道——那是墙的领域知识。 解法是让 builder 返回一个「信封」： 

root（信封，会被丢掉）
 └─ body（带 position + rotation.y）
     └─ mesh（顶点是局部坐标）

GeometrySystem 取的是 root.children， 所以 body 连同它的 transform 一起被挂到注册的 group 上。 Rule ② 的实质（不许把世界坐标烘进顶点）仍然成立—— 顶点是局部的，世界位置在 body.position 上。 M6 的 slab / column 有 position 字段，可以走规格书的原路； 两条路并存不冲突。

幂等不是为了省事

React 严格模式会把 useState 的初始化函数跑两次， 第二次会撞上 registerNode 的「已经注册过了」。 所以 registerAllNodes 用模块级 let registered 守卫 —— 但 registerNode 本身仍然抛， 因为「两个文件声明了同一个 kind」是真 bug，必须炸出来。 把「重入保护」和「冲突检测」放在两个不同的层次上。

为什么不用 import 副作用（在 definition.ts 末尾直接 registerNode(...)）：那依赖「有人 import 了这个文件」， 而 tree-shaking 会积极地帮倒忙。症状是生产构建里节点画不出来，开发时一切正常。

每帧两个阶段：

阶段一 —— 按类型批处理
  脏节点里出现过的每一种 kind，若声明了 computeLevelData：

__fromGeometry 现在做，三行；M7 补做，重读整条 dispose 路径

一个注册的 group 会同时挂两种子节点：builder 造的网格、 和 React 渲染的宿主子节点（M7 的门窗）。不打标记就分不清， 重建时会把 React 挂的那些一起 dispose 掉 —— 症状是把门拖到墙上，门消失且再也不回来。 M5 还没有宿主，但代价是三行。

import * as THREE from 'three'
import { midpoint, type Point2D } from '../../../core/lib/geometry-2d'
import type { GeometryContext, NodeAppearance } from '../../../core/registry/node-definition'
import { getWallHeight, type WallNode } from '../../../core/schema/wall'
import { getWallPlanFootprint } from '../../../core/systems/wall/wall-footprint'
import { calculateLevelMiters, type MiterData } from '../../../core/systems/wall/wall-mitering'

const WALL_COLOR = '#e8e8e8'
const WALL_SELECTED_COLOR = '#7dd3c0'

const toPoint = (t: readonly [number, number]): Point2D => ({ x: t[0], y: t[1] })

export function worldToLocalXZ(
  p: Point2D,
  position: [number, number, number],
  rotationY: number,
): Point2D {
  const cos = Math.cos(rotationY)
  const sin = Math.sin(rotationY)
  const dx = p.x - position[0]
  const dz = p.y - position[2]
  return { x: dx * cos - dz * sin, y: dx * sin + dz * cos }
}

export function wallTransform(wall: WallNode): {
  position: [number, number, number]
  rotationY: number
} {
  const start = toPoint(wall.start)
  const end = toPoint(wall.end)
  const c = midpoint(start, end)
  const rotationY = Math.atan2(-(end.y - start.y), end.x - start.x)
  return { position: [c.x, 0, c.y], rotationY }
}

/** `def.computeLevelData` —— 整层跑一次，产物落进 `ctx.levelData`。 */
export function computeWallLevelMiters(walls: readonly WallNode[]): MiterData {
  return calculateLevelMiters([...walls])
}

/**
 * `def.geometry` —— 纯函数。不 import useScene，不碰 store。
 *
 * ⚠ 返回值的结构值得看清楚：**外层 root 只是个信封**。
 * GeometrySystem 取的是 `root.children`，把它们挂到注册的 group 上。
 * 所以墙的位置/朝向必须挂在 `body` 上（root 的子节点），
 * 挂在 root 上会被连信封一起丢掉。
 *
 * 为什么墙的 transform 由 builder 算，而不是像规格书 Rule ② 说的
 * 「渲染器拥有 transform」：**我们的 WallNode 根本没有 position 字段**。
 * 它由 start / end 两个点定义（D3），中心和朝向是导出量。
 * 通用渲染器不知道怎么从 start/end 推 transform，也不该知道 ——
 * 那是墙这一类的领域知识。Rule ② 的实质（不许把世界坐标烘进顶点）
 * 仍然成立：顶点是局部的，世界位置在 body.position 上。
 */
export function buildWallGeometry(
  node: WallNode,
  ctx: GeometryContext<MiterData>,
  appearance: NodeAppearance,
): THREE.Object3D {
  const root = new THREE.Group()

  const miter = ctx.levelData ?? calculateLevelMiters([node])
  const worldFootprint = getWallPlanFootprint(node, miter)
  if (worldFootprint.length < 3) return root

  const { position, rotationY } = wallTransform(node)
  const local = worldFootprint.map((p) => worldToLocalXZ(p, position, rotationY))

  const shape = new THREE.Shape()
  shape.moveTo(local[0]!.x, -local[0]!.y)
  for (let i = 1; i < local.length; i += 1) shape.lineTo(local[i]!.x, -local[i]!.y)
  shape.closePath()

  const geometry = new THREE.ExtrudeGeometry(shape, {
    depth: getWallHeight(node),
    bevelEnabled: false,
  })
  geometry.rotateX(-Math.PI / 2)

  const material = new THREE.MeshStandardMaterial({
    color: appearance.selected ? WALL_SELECTED_COLOR : WALL_COLOR,
    roughness: 0.9,
    metalness: 0,
  })

  const mesh = new THREE.Mesh(geometry, material)
  mesh.name = 'wall-body'
  mesh.castShadow = true
  mesh.receiveShadow = true

  const body = new THREE.Group()
  body.position.set(position[0], position[1], position[2])
  body.rotation.y = rotationY
  body.add(mesh)

  root.add(body)
  return root
}

import { useContext, useRef } from "react";
import type * as THREE from 'three'

import { nodeRegistry } from "../../core/registry/node-registry";
import type { GeometryContext } from "../../core/registry/node-definition";
import { sceneRegistry } from "../../core/registry/scene-registry";
import type { AnyNode, AnyNodeId, AnyNodeType } from "../../core/schema/types";
import { getEffectiveNode } from "../../core/store/use-live-overrides";
import { useScene } from "../../core/store/use-scene";
import { SelectionContext } from "../components/scene-context";

/**
 * 通用几何系统。每帧：
 *   脏集 → 查 def.geometry → 建 → 换子节点 → 清脏。
 *
 * 对照仓库同名文件是 441 行，多出来的是 geometryKey 跳过、surfaceRole
 * 主题着色、场景材质库、appearance 变化时的全量重标脏 —— 全是 M7/M14 的东西。
 */
export function GeometrySystem(): null {
    // dirtyNodes 是可变 Set，引用永远不变，所以这个订阅永远不会触发 ——
    // 我们要的就是那个稳定引用，每帧自己读 .size。
    const dirtyNodes = useScene((s) => s.dirtyNodes)

    // 选中态是「呈现意图」，不是几何输入，但 builder 要用它选颜色。
    // 放 ref 里避免 selectId 变化时重建整个 useFrame 闭包。
    const selectId = useContext(SelectionContext)
    const selectIdRef = useRef(selectId)
    selectIdRef.current = selectId

    useFrame(() => {
        if (dirtyNodes.size === 0) return

        const { nodes, clearDirty } = useScene.getState()
        const dirtyIds = [...dirtyNodes] as AnyNodeId[]

        // ── 阶段一：按类型批处理 ────────────────────────────────
        // 声明了 computeLevelData 的类型，整层跑一次，产物给这一类共用。
        // 墙的斜接是动机：逐墙算是 O(N²)，而且拖一堵墙时每个邻居都会
        // 各自算一遍完整的交点图。
        const levelDataByKind = new Map<AnyNodeType, unknown>()
        const effectiveByKind = new Map<AnyNodeType, AnyNode[]>()

        for (const id of dirtyIds) {
            const node = nodes[id]
            if (!node) continue
            const def = nodeRegistry.get(node.type)
            if (!def?.computeLevelData || levelDataByKind.has(node.type)) continue

            const siblings = Object.values(nodes)
                .filter((n) => n.type === node.type)
                .map((n) => getEffectiveNode(n))
            effectiveByKind.set(node.type, siblings)
            levelDataByKind.set(node.type, def.computeLevelData(siblings))
        }

        // ── 阶段二：逐个重建 ────────────────────────────────────
        for (const id of dirtyIds) {
            const documentNode = nodes[id]
            if (!documentNode) {
                clearDirty(id)          // 节点已删，脏标记跟着走
                continue
            }

            const def = nodeRegistry.get(documentNode.type)
            if (!def?.geometry) {
                clearDirty(id)          // 这一类不走通用几何路径
                continue
            }

            const group = sceneRegistry.nodes.get(id) as THREE.Group | undefined
            if (!group) {
                // ⚠ 故意**不**清脏。渲染器还没挂载完（第一帧、或读档后
                //   React 还在 commit），下一帧再来。清了的话这个节点
                //   就永远不会被建出来 —— 症状是「读档后场景空白，
                //   直到你动一下鼠标才冒出来」。
                continue
            }

            const node = getEffectiveNode(documentNode)
            const siblings =
                effectiveByKind.get(node.type) ??
                Object.values(nodes)
                    .filter((n) => n.type === node.type)
                    .map((n) => getEffectiveNode(n))

            const ctx: GeometryContext = {
                resolve: (target) => nodes[target],
                siblings,
                levelData: levelDataByKind.get(node.type),
            }

            const built = def.geometry(node, ctx, { selected: selectIdRef.current === id })

            disposeGeometryChildren(group)
            // 从后往前搬：built.children 会随着 group.add 就地缩短。
            for (const child of [...built.children]) {
                child.userData.__fromGeometry = true
                group.add(child)
            }

            clearDirty(id)
        }
    })

    return null
}

/**
 * 只 dispose 上一轮 builder 产出的子节点。
 *
 * 一个注册的 group 会同时挂两种子节点：builder 造的网格，
 * 和 React 渲染的宿主子节点（M7 的门窗）。不打标记就分不清 ——
 * 症状是把门拖到墙上，门消失且再也不回来。
 *
 * M5 还没有宿主，但现在做只要三行，M7 补做要重新理解整条 dispose 路径。
 */
function disposeGeometryChildren(group: THREE.Group): void {
    for (const child of [...group.children]) {
        if (child.userData.__fromGeometry !== true) continue
        group.remove(child)
        disposeSubtree(child)
    }
}

function disposeSubtree(object: THREE.Object3D): void {
    object.traverse((node) => {
        const mesh = node as Partial<THREE.Mesh>
        mesh.geometry?.dispose()
        const material = mesh.material
        if (Array.isArray(material)) for (const m of material) m.dispose()
        else material?.dispose()
    })
}
